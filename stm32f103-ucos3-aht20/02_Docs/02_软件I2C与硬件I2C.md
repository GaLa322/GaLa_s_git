# 软件 I2C 与硬件 I2C 有什么区别？（任务二第 1 小问）

> 对应教材：野火《STM32F103 开发指南》第 23 章 "I2C--读写 EEPROM" 原理部分。
> 本文在讲清原理的同时，给出**本项目里两份真实可编译的代码**，方便对照理解。

---

## 1. 先把 I2C 本身说清楚

I2C（Inter-Integrated Circuit）是飞利浦提出的一种**两线制、半双工、多主多从**的同步串行总线。

### 1.1 物理层：两根线 + 上拉电阻

| 信号 | 作用 |
| --- | --- |
| SCL | 串行时钟，由主机产生 |
| SDA | 串行数据，双向 |

关键点：**两根线都是开漏（open-drain）输出**，只能主动拉低，不能主动拉高。
高电平靠**外部上拉电阻**（典型 4.7 kΩ）拉上去。由此产生两个重要特性：

1. **"线与"（wired-AND）**：只要有一个设备把线拉低，整条线就是低电平。
   - 从机可以拉低 SDA 表示 ACK；
   - 多主机时，谁拉低谁"赢"，输的那个自动退出 —— 这叫**总线仲裁**。
2. **时钟同步**：从机如果来不及处理，可以把 SCL 拉低"按住时钟"，主机必须等它 —— 这叫**时钟拉伸**。

正因为开漏，软件 I2C 只要把 GPIO 配成**开漏输出**就能模拟；配成推挽就违反协议了
（两个设备一个要拉高一个要拉低时会短路）。

### 1.2 协议层：START / 数据 / ACK / STOP

```text
       START                                    STOP
SCL ‾‾‾\___/‾‾‾\_/‾‾‾\_/‾‾‾\_/‾‾‾\_/‾‾‾\_/‾‾‾\_/‾‾‾\_/‾‾‾\_/‾‾‾\___/‾‾‾‾‾
SDA ‾‾‾‾\_______X_______X_______X_______X_______X_______X_______X_______/‾‾‾‾‾
        │  bit7   bit6    ...                                    ACK │
        └ 起始条件（SCL 高时 SDA 下降）
```

| 时序单元 | 定义 |
| --- | --- |
| **START** | SCL 保持高电平时，SDA 由高变低 |
| **STOP** | SCL 保持高电平时，SDA 由低变高 |
| **数据位** | SCL 低电平时准备数据，SCL 高电平时数据必须稳定（接收方在 SCL 上升沿采样） |
| **ACK** | 主机发完 8 bit 后释放 SDA，从机在第 9 个时钟把 SDA 拉低表示"收到" |
| **NACK** | 第 9 个时钟 SDA 保持高，表示"没收到/不要了"（读最后一个字节时主机发 NACK） |
| **重复起始（Sr）** | 不发 STOP 直接再发一个 START，用于"写地址 → 读数据"切换方向 |

### 1.3 一次完整的 AHT20 读数据

```text
START → 0x70(W) → ACK → 0xAC → ACK → 0x33 → ACK → 0x00 → ACK → STOP
       （等 80ms）
START → 0x71(R) → ACK → [7 字节数据，前 6 个 ACK，最后一个 NACK] → STOP
```

`0x70` 就是 7 位地址 0x38 左移一位再或上读写位（0=写，1=读）。

## 2. 什么是"软件 I2C"

**软件 I2C（Software I2C / Bit-banging）**：不用芯片内部的 I2C 外设，
而是**用两个普通 GPIO 口，由 CPU 一条指令一条指令地把 SCL/SDA 按协议时序拉高拉低**。

核心代码就四段（本项目 `Src/bsp_i2c_sw.c`，已裁剪）：

```c
/* ① 起始条件：SCL 高时 SDA 下降 */
static void I2C_Start(void)
{
    SDA_HIGH(); SCL_HIGH(); I2C_DelayUs(5);
    SDA_LOW();              /* ← 这一下就是 START */
    I2C_DelayUs(5);
    SCL_LOW();  I2C_DelayUs(5);
}

/* ② 写一个字节 + 读 ACK */
static uint8_t I2C_WriteByte(uint8_t byte)
{
    for (i = 0; i < 8; i++) {
        if (byte & 0x80) SDA_HIGH(); else SDA_LOW();   /* 先摆好数据 */
        byte <<= 1;
        I2C_DelayUs(2);
        SCL_HIGH(); I2C_DelayUs(5);                   /* 上升沿，从机采样 */
        SCL_LOW();  I2C_DelayUs(2);
    }
    SDA_HIGH();                                       /* 释放 SDA 等 ACK */
    I2C_DelayUs(2); SCL_HIGH(); I2C_DelayUs(2);
    ack = (SDA_READ() == GPIO_PIN_RESET) ? 1 : 0;     /* 第 9 个时钟读 SDA */
    SCL_LOW(); I2C_DelayUs(2);
    return ack;
}

/* ③ 读一个字节 + 发 ACK/NACK（略，见源码） */
/* ④ 停止条件：SCL 高时 SDA 上升 */
```

延时用 DWT 周期计数器做，比 `for` 循环准：

```c
CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;   /* 打开 DWT */
DWT->CTRL |= DWT_CTRL_CYCCNTENA_Msk;              /* 使能周期计数器 */
s_cycles_per_us = SystemCoreClock / 1000000U;     /* 8 MHz → 8 个周期/μs */

static void I2C_DelayUs(uint32_t us)
{
    uint32_t start = DWT->CYCCNT;
    while ((DWT->CYCCNT - start) < us * s_cycles_per_us) { }
}
```

### 软件 I2C 的优点

| 优点 | 说明 |
| --- | --- |
| **引脚随便挑** | 任何 GPIO 都行，PCB 布线/引脚冲突时救命 |
| **时序完全可控** | 想跑 10 kHz 就 10 kHz，遇到"慢速器件"很好用 |
| **不受外设限制** | 芯片没有 I2C 外设、或者 I2C 外设被占满时照用 |
| **移植性极强** | 换到 51、AVR、国产 MCU 上，改改 GPIO 宏就能跑 |
| **调试直观** | 出问题可以单步看每条线的电平，逻辑分析仪上一目了然 |

### 软件 I2C 的缺点

| 缺点 | 说明 |
| --- | --- |
| **占 CPU** | 传 1 字节要几十条指令 + 忙等延时，全程 CPU 陪着 |
| **速度上不去** | 一般 100~200 kHz，想跑 400 kHz 需要很精细的延时 |
| **时序受中断影响** | 传到一半来个中断，SCL 被拉长，从机可能超时（AHT20 不严格，EEPROM 也不严格，但有些器件会） |
| **速率不准** | 依赖 `SystemCoreClock` 和编译器优化等级，优化等级一变速率就变 |
| **代码量大** | 要自己实现 START/STOP/ACK/仲裁/总线恢复 |

### 软件 I2C 什么时候用

- 引脚被别的功能占了，只能挪到别的脚；
- 多路 I2C 需要"软切换"（比如 4 路传感器用 4 组 GPIO 分时复用）；
- 芯片的硬件 I2C 有坑（**STM32F103 的 I2C 外设就是著名的"有坑"**）；
- 初学者第一次学 I2C 协议 —— **强烈建议先写一遍软件 I2C**，写完你就真的懂时序了。

## 3. 什么是"硬件 I2C"

**硬件 I2C**：使用芯片内部的 I2C 外设。你只需要：

1. 把数据写进 `DR`（数据寄存器）；
2. 外设**自动**产生 START、8 个时钟、第 9 个 ACK 时钟、STOP；
3. 通过状态寄存器和中断/DMA 知道"发完了/收到了/NACK 了"。

在 HAL 库里就是一行：

```c
HAL_I2C_Master_Transmit(&hi2c1, 0x38 << 1, cmd, 3, 50);   /* 发 3 字节 */
HAL_I2C_Master_Receive (&hi2c1, 0x38 << 1, buf, 7, 50);   /* 收 7 字节 */
```

看起来简单，但里面的状态机很复杂：`BUSY / MSL / TRA / TXE / RXNE / BTF / AF / ARLO / BERR`……
HAL 库帮你把这些都封起来了。

### 硬件 I2C 的优点

| 优点 | 说明 |
| --- | --- |
| **省 CPU** | 传输由硬件完成，CPU 可以干别的（配 DMA 更是零占用） |
| **速率高且准** | 100 kHz / 400 kHz / 1 MHz 由时钟分频精确产生 |
| **支持中断/DMA** | 大量数据搬运（如 OLED 刷屏）效率高 |
| **自动处理仲裁/时钟同步** | 多主机场景更可靠 |
| **时序标准** | 上升沿、保持时间都由硬件保证，示波器上看很漂亮 |

### 硬件 I2C 的缺点

| 缺点 | 说明 |
| --- | --- |
| **引脚固定** | 只能用外设映射的那几个脚（STM32F103 的 I2C1 是 PB6/PB7 或重映射到 PB8/PB9） |
| **STM32F1 的 I2C 外设 bug 多** | 早期硅版本有"BUSY 卡死""发送中丢中断"等勘误，很多人被坑过 |
| **配置复杂** | 时钟、上拉、超时、错误处理，一个没配好就卡在 `HAL_I2C_Master_Transmit` 里 |
| **出错后难恢复** | 一旦总线锁死，需要手动复位外设（`HAL_I2C_DeInit` + `Init`）+ 打 9 个时钟 |
| **调试不直观** | 出问题只能看状态寄存器，不如软件 I2C 好单步 |

### STM32F1 硬件 I2C 的几个实际经验

1. **一定要加上拉**：4.7 kΩ 到 3.3V。F1 的 I2C 引脚是复用开漏，没有内部上拉可用。
2. **超时要给足**：`HAL_I2C_Master_Transmit(..., 50)` 里的 50 ms 是超时，不是传输时间；
   给太小（比如 1 ms）在 100 kHz 下正常传输都会超时。
3. **卡死在 BUSY**：如果上一次传输被复位打断，`I2C_FLAG_BUSY` 可能一直是 1。
   解决办法：`HAL_I2C_DeInit()` → 把 SCL 当普通 GPIO 打 9 个时钟 → `HAL_I2C_Init()`。
   本项目软件 I2C 里的 `I2C_BusRecover()` 就是这个思路。
4. **不要在没有上拉的情况下调试**：现象是 `HAL_I2C_Master_Transmit` 永远返回 `HAL_ERROR`，
   用示波器看 SDA 一直是低电平。

## 4. 一张表说清区别

| 维度 | 软件 I2C | 硬件 I2C |
| --- | --- | --- |
| 引脚 | 任意 GPIO | 固定（I2C1: PB6/PB7） |
| CPU 占用 | 高（全程忙等） | 低（硬件搬运，可配 DMA） |
| 速率 | 通常 ≤ 200 kHz，不准 | 100/400 kHz，精确 |
| 代码量 | 大（自己写时序） | 小（调 HAL） |
| 时序可靠性 | 受中断/优化等级影响 | 硬件保证 |
| 出错恢复 | 容易（自己控制） | 需要 DeInit/Init + 总线恢复 |
| 多主机仲裁 | 需要自己实现 | 硬件自动 |
| 学习价值 | **极高**（写完就懂协议） | 一般（会被 HAL 挡住细节） |
| 典型场景 | 引脚受限、多路复用、F1 硬件 I2C 踩坑 | 高速、大数据量、多设备共享总线 |

## 5. 本项目怎么"一份驱动、两种实现"

`AHT20` 驱动**完全不知道**底下是软件还是硬件 I2C，它只调用三个函数：

```c
/* Inc/bsp_i2c.h */
uint8_t BSP_I2C_Init(void);
uint8_t BSP_I2C_Write(uint8_t addr7, const uint8_t *data, uint16_t len);
uint8_t BSP_I2C_Read (uint8_t addr7, uint8_t *data, uint16_t len);
```

然后由 `board_config.h` 里的一个宏决定编译哪一份实现：

```c
#define APP_I2C_USE_SOFT   0    /* 0 = 硬件 I2C1，1 = 软件 I2C（PB6/PB7） */
```

- `Src/bsp_i2c_hw.c`：`#if (APP_I2C_USE_SOFT == 0)` 才编译，内部就是 `HAL_I2C_Master_Transmit/Receive`；
- `Src/bsp_i2c_sw.c`：`#if (APP_I2C_USE_SOFT == 1)` 才编译，内部是上面那套位翻转。

### 5.1 怎么切换并验证

1. 把 `APP_I2C_USE_SOFT` 改成 `1`，重新编译下载；
2. 串口横幅会变成：

   ```text
   I2C  : 软件模拟 (GPIO) @ PB6/PB7, AHT20 addr 0x38
   ```

3. 功能应该**完全一样**（温湿度照常输出）；
4. 用逻辑分析仪对比两种实现的 SCL 波形：
   - 硬件 I2C：波形规整，400 kHz；
   - 软件 I2C：约 100 kHz，周期略有抖动（因为每条指令耗时不同）。

这一步本身就是很好的实验记录素材，报告里可以放两张波形图对比。

### 5.2 为什么值得写两份

1. 作业第 1 小问要求"解释软件 I2C 和硬件 I2C"——**有代码比有嘴强**；
2. 万一你的板子硬件 I2C 有坑（F1 很常见），改一个宏就能救场，不影响交作业；
3. 软件 I2C 那份代码把 START/ACK/STOP 全写明了，答辩时可以直接指着讲时序。

## 6. 顺带说清：EEPROM 和 AHT20 的访问方式不一样

野火第 23 章讲的是 AT24C02 EEPROM，它是"**有寄存器地址**"的器件：

```text
写：START → 0xA0(W) → ACK → 字地址 → ACK → 数据 → ACK → STOP
读：START → 0xA0(W) → ACK → 字地址 → ACK → Sr → 0xA1(R) → ACK → 数据 → NACK → STOP
```

注意读的时候要**先写地址、再重复起始、再切读**（"伪写"）。

而 AHT20 是"**命令式**"器件，没有寄存器地址，直接发命令字节：

```text
触发：START → 0x70(W) → ACK → 0xAC → ACK → 0x33 → ACK → 0x00 → ACK → STOP
读取：START → 0x71(R) → ACK → 7 字节 → NACK → STOP
```

共同点是：都用 7 位地址 + 读写位、都要 ACK、都要上拉。区别只是"第二段发什么"。
理解了 EEPROM，AHT20 只是换了命令字而已。

## 7. 答辩可能被问到的几个问题

**Q1：软件 I2C 为什么必须配成开漏输出？**
A：因为 I2C 是"线与"总线，多个设备可能同时驱动 SDA。推挽输出时一个设备输出高、另一个输出低，
会形成短路大电流。开漏 + 上拉才能实现"任何一个拉低就是低电平"。

**Q2：软件 I2C 传输过程中被中断打断会怎样？**
A：SCL 会被拉长（时钟拉伸），只要从机不超时就没事。AHT20、AT24C02 都允许任意长的 SCL 低电平。
但如果是"时序要求严格"的器件（某些传感器），长时间中断会导致通信失败，这时要关中断或用硬件 I2C。

**Q3：硬件 I2C 传输失败了怎么恢复？**
A：先 `HAL_I2C_DeInit()`，把 SCL/SDA 当普通 GPIO 输出 9 个时钟（把从机里可能卡住的位移出去），
再发 STOP，最后 `HAL_I2C_Init()` 重新初始化。本项目 `I2C_BusRecover()` 就是这段逻辑。

**Q4：为什么 AHT20 的地址是 0x38，代码里左移一位？**
A：0x38 是 7 位地址。I2C 帧里的第一个字节是 `地址<<1 | R/W`，所以写是 0x70、读是 0x71。
HAL 库的接口要求传"左移后的 8 位地址"，所以我们写 `0x38 << 1`。
（CubeMX 生成的 I2C 扫描代码里常看到 `0x38<<1`，就是这个原因。）

**Q5：I2C 最多能挂多少设备？**
A：7 位地址理论上 127 个（0x00~0x7F，其中 0x00 广播、0x01~0x07 保留）。
实际受总线电容限制（标准模式 ≤ 400 pF），线越长能挂的越少。
